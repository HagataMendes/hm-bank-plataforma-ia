01

Contexto & objetivo

A vaga pede alguém que transite entre front-end (React/TypeScript), backend (Python, FastAPI, SQL) e infraestrutura AWS serverless, com diferenciais em RAG, sistemas multi-agente, DDD e Data Mesh. Em vez de listar isso num currículo, decidi construir a interface de uma plataforma de IA corporativa que já nasce pensando nessa arquitetura — mesmo que, por limitação de ambiente, o backend e a nuvem sejam simulados no front-end.

Nota de escopo. "HM Bank" é uma marca fictícia; todos os dados, métricas e respostas dos agentes são simulados no navegador — sem backend real, sem LLM real, sem dado de nenhuma empresa. O objetivo é demonstrar raciocínio de produto, arquitetura e front-end, não uma integração real.

O que a interface precisava provar

  • Raciocínio de sistema, não de tela solta — a UI reflete uma arquitetura de múltiplos agentes especializados coordenados por um orquestrador, do jeito que a vaga descreve.
  • Domínio do front-end pedido — React + TypeScript, tema por tokens, estado centralizado, sem framework de UI pronto.
  • Consciência da nuvem por trás — cada tela tem uma contraparte de infraestrutura AWS pensada e documentada aqui, mesmo que simulada.
02

Arquitetura de front-end

SPA em React 18 + TypeScript, com sistema de temas por tokens CSS (claro/escuro) e todo o estado centralizado num único componente <App/>, que repassa dados para componentes de apresentação — o mesmo padrão que eu usaria num projeto real antes de introduzir uma lib de state management.

Árvore de componentes (simplificada)

<App> // estado global: view, activeId, threads, tema…
├─ <Sidebar>
│  ├─ <IconRail> Mensagens · IA · Agenda
│  └─ <SidebarPanel> lista conforme a aba do rail
├─ <Topbar> breadcrumb, ambiente, tema, usuário
├─ <ChatThread>
│  └─ <MessageBubble> texto, SQL, NoSQL, ML, upload
└─ <GovernancePanels> Dashboard, Guardrails, Acesso, Nuvem

Decisões e por quê

DecisãoMotivação
Design tokens em CSSPaleta e espaçamento como variáveis, redefinidas em três camadas — :root, prefers-color-scheme e [data-theme] — cobrindo tema do sistema e escolha manual sem duplicar componentes.
Componentes pequenos e compostosNavItem, AgentAvatar, MessageBubble combinados em telas maiores — a mesma lógica que eu aplicaria com uma lib de componentes real.
Estado como "backend simulado"Respostas, latência e eventos de auditoria vivem em useState/useEffect, desenhados para virar chamadas de API (fetch/React Query) sem reescrever a UI.

Próximo passo natural: micro-frontends

Hoje cada painel (chat, dashboard, governança) é um componente no mesmo bundle. Como a vaga cita Webpack Module Federation como diferencial, o passo seguinte seria expor "Central de Inteligência", "Governança" e "Mensagens" como micro-frontends independentes, cada um com deploy próprio, compartilhando apenas o design system e a casca de navegação.

Solução em nuvem (simulada)

Nenhuma dessas peças está no ar — mas cada tela da interface foi desenhada como se estivesse conversando com esta arquitetura. É o desenho que eu levaria para uma reunião de arquitetura antes de escrever a primeira linha de backend.

04

Sistema multi-agente & RAG

Em vez de um chatbot único, a plataforma tem um orquestrador (Beto) e nove agentes especialistas — cada um dono de um domínio de negócio, no espírito de Domain-Driven Design: o agente Jurídico não enxerga dado de RH, o Financeiro não enxerga dado de Risco.

MecanismoComo funciona
Classificação de intençãoO texto do usuário passa por um classificador leve (hoje por palavras-chave; no mundo real, um modelo de intenção) que decide se a pergunta fica com o orquestrador ou vai para um especialista.
RAG com fonte citadaToda resposta baseada em documento mostra a fonte e um score de confiança — pensado para o requisito de rastreabilidade que um banco exige de qualquer resposta gerada por IA.
Guardrails por agenteUm painel de auditoria mostra, por agente, o que foi bloqueado ou mascarado — a camada de governança que costuma faltar em demos de IA generativa.
05

Dados: relacional, não-relacional e em malha

A vaga pede trânsito entre bancos relacionais e não-relacionais, além de Data Warehouse/Lakehouse/Data Mesh como diferencial. Simulei os três na própria conversa:

CamadaComo aparece na interface
SQL (RDS PostgreSQL)O agente Analista de Dados devolve a query gerada, uma tabela de resultado e o tempo de execução — como um Text-to-SQL real faria.
NoSQL (DynamoDB)Consultas de sessão e perfil respondem no formato chave-valor, com o item bruto exibido — deixando claro quando a modelagem é de documento, não relacional.
Data Mesh / LakehouseCada agente de negócio é dono da sua própria fonte de dados (contratos, políticas de crédito, CRM); o Analista de Dados consulta o lakehouse central, não os dados de domínio de outro time.
06

Decisões tela a tela

Os quatro esquemas abaixo são wireframes — não screenshots — feitos para explicar o raciocínio por trás de cada tela sem depender de capturas reais.

01

Chat multi-agente

A coluna de agentes fica sempre visível — reforça que existem vários especialistas, não um chatbot genérico. Cada bolha carrega fonte, confiança e versão do modelo.

02

Dashboard & eventos

Métricas de consumo por agente, latência média e um feed de eventos técnicos — a interface assume observabilidade como parte do produto, não um extra.

03

Agenda & mensagens

Separadas do menu da IA numa coluna própria de "aplicativos" — a plataforma tratada como suíte corporativa completa, com a IA como um app dentro dela.

04

Governança & nuvem

Log de auditoria de prompts, matriz de acesso por departamento e status dos serviços AWS — a camada que costuma faltar em demos de IA.

07

Mapeamento com os requisitos da vaga

Esperado foi implementado ou simulado diretamente na interface. Diferencial foi pensado na arquitetura e documentado aqui como próximo passo.

RequisitoO que existe no protótipo
coreReact.js + TypeScriptFront-end inteiro em React + TypeScript, sem framework de UI pronto, com sistema de tema por tokens.
corePython, SQL, FastAPI/DRFSimulados na camada de agentes (Text-to-SQL, Analista de Dados) e documentados como a API que o front-end consumiria via FastAPI.
coreAWS serverless (Lambda, API Gateway, ECS, SQS, DynamoDB, RDS)Diagrama de arquitetura completo (seção 03) com o papel de cada serviço no fluxo síncrono e assíncrono.
coreTestes, CI/CD, IaC, assistentes de códigoCloudFormation citado como padrão de IaC; pipeline de deploy simulado no painel de Status da Nuvem.

diferencialDDDCada agente é um domínio isolado (Jurídico, Financeiro, RH, CRM, Risco…), com controle de acesso por departamento na Governança.
diferencialData Warehouse / Lakehouse / Data MeshSeção de Dados (05) descreve a malha de dados por domínio e o papel do lakehouse central.
diferencialKubernetesEKS desenhado como host dos modelos clássicos de ML (scoring de risco).
